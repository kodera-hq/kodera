# ADR-0009: Core-owned primary identifiers use UUIDv7

**Status:** Accepted
**Deciders:** zôÖma, the product owner, who decided that Core-owned primary identifiers are server-generated UUIDv7 values exactly as this record states them.

## Context

When this record was proposed, the domain model specified ULIDs while the Core
API contract exposed every resource identifier as an OpenAPI `uuid`; the model
(`docs/domain/MODEL.md`) has specified UUIDv7 since. Leaving both choices in
place would have forced the first migration either to invent a compatibility
layer or to ship a breaking contract change immediately after implementation
began.

The control plane needs identifiers that are safe to create before a database
round trip, work with PostgreSQL and Django, do not expose sequential customer
counts, and remain reasonably local in database indexes. Clients do not sort,
authorise, or infer business state from an identifier.

PostgreSQL 16 stores every RFC UUID version in its native `uuid` type but does
not generate UUIDv7 itself. Python 3.12 likewise has no standard-library UUIDv7
generator. Generation therefore needs one deliberately selected and pinned
RFC 9562 implementation until the runtime baseline supplies it.

## Decision

- Every primary key generated by Core is a server-generated UUIDv7 stored in a
  PostgreSQL `uuid` column and rendered in canonical lower-case UUID form.
- Foreign keys use the same native type. OpenAPI continues to declare these
  values as `type: string, format: uuid`; generated clients treat them as
  opaque strings.
- Provider identifiers and Keycloak subjects retain the type and value issued
  by their owner. They are not rewritten as Core UUIDv7 values.
- Human addressing keys such as tenant slugs and catalogue codes remain
  separate from primary keys and keep their existing reservation rules.
- Correct ordering always uses an explicit timestamp followed by the UUID as a
  deterministic tie-breaker. Business correctness MUST NOT depend on decoding
  or comparing the timestamp embedded in UUIDv7.
- Identifier opacity is not an authorisation control. Every lookup remains
  organisation-scoped and returns the same not-found result for an invisible
  object.
- Client-generated idempotency keys remain a separate opaque string contract;
  UUIDv4 is the recommended client value.
- Before the first migration, the domain-kernel specification MUST name the
  pinned generator, test the version and variant bits, and test collision
  handling.
- Before the first route that accepts a Core-owned identifier is served, a test
  MUST prove that invalid or non-canonical identifiers are rejected at the API
  boundary.

## Options considered

| Option | Decision |
|---|---|
| Sequential integers | Rejected. They disclose record counts, couple creation to one database and are already excluded by the public contract. |
| UUIDv4 | Viable but rejected for Core primary keys. It keeps native storage and mature generators but gives append-heavy indexes no time locality. It remains the client recommendation for idempotency keys. |
| ULID | Rejected. It preserves time ordering but requires a custom database and API representation while the contract, PostgreSQL and Django already speak UUID. |
| UUIDv7 | Chosen. It is an RFC-standard, time-ordered UUID that preserves the existing wire type and PostgreSQL native storage. |

## Consequences

- The identifier mismatch closes before any migration or generated client is
  treated as stable.
- Core needs one small generation dependency while Python 3.12 remains the
  runtime baseline; a home-grown generator is not acceptable.
- UUIDv7 reveals an approximate creation time. Identifiers are therefore never
  treated as secrets and never substitute for object-level authorisation.
- Audit ordering and cursor pagination keep explicit time columns, so a later
  generator change cannot change business ordering.
- Contract examples should use version-7 values before the first generated
  client and mock release, even though their OpenAPI type remains `uuid`. When
  the owner decided this record, the examples of Core-owned identifiers in both
  OpenAPI contracts and in `contracts/examples/` were still version-4 values.
  The client and mock generation that `contracts/README.md` describes was not
  wired, and the console generated its own client and mock from contract
  0.11.0. Moving the examples to version-7 values is owed before that
  generation is wired, and with the next version of each contract at the
  latest; it changes examples only, which `contracts/README.md` classes as a
  patch.
- When the owner decided this record, the first migrations existed, and the
  three conditions the decision sets before the first migration were met by the
  change that added them. No document is called the domain-kernel
  specification: `docs/specs/CUSTOMER_PERSISTENCE.md` names the pinned
  generator and states the collision rule, `tests/test_customer_ids.py` tests
  the version and variant bits, and `tests/test_customer_persistence_models.py`
  tests that a primary-key collision is refused and leaves the existing row
  unchanged. No served route accepted a Core-owned identifier (`config/urls.py`,
  `config/customer_urls.py`), so the rejection proof the decision requires
  before the first such route was not yet due and did not exist.
