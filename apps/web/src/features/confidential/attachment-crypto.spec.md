# Confidential attachment cryptography

Status: Worker-internal primitive implemented in source; product integration and browser qualification remain pending.

`attachment-crypto.worker.ts` provides real WebCrypto AES-256-GCM attachment encryption and decryption. It refuses a document-context import and performs no network or persistence operations. Only the fixed confidential worker may import this implementation. The primitive does not establish a room session, current membership, trusted device identity or permission to send. Its caller must enforce those boundaries before encryption, after every asynchronous completion and before publishing results.

## Closed contract

`encryptConfidentialAttachment({ context, plaintext })` accepts canonical non-nil lowercase room and attachment UUIDs, a nonnegative safe-integer epoch, and an ordinary fixed-buffer Uint8Array of 1 through 26,214,384 bytes. It synchronously copies inputs, generates an independent random 32-byte key and 12-byte IV, imports a non-extractable AES-GCM key and authenticates the UTF-8 encoding of `JSON.stringify(['kodera-confidential-attachment', 1, roomId, epoch, attachmentId])`. The 128-bit authentication tag is included in the returned ciphertext. Ciphertext fits the existing 25 MiB object bound; the plaintext limit reserves its 16-byte tag.

The result contains a ciphertext copy owned by the caller, a frozen public upload descriptor containing exactly version, algorithm, ciphertext SHA-256 and ciphertext byte count, and a sensitive canonical JSON secret descriptor. The latter contains exactly version, algorithm, roomId, epoch, attachmentId, keyBase64, ivBase64, ciphertextSha256 and ciphertextBytes in that order. Keys and IVs use canonical padded Base64. The descriptor must remain inside the worker and be sealed inside a genuine authenticated encrypted room application payload. It must never be included in an upload ticket, storage request, telemetry, log or unencrypted Core request. Original filenames and MIME types likewise belong inside that encrypted payload; eventual uploads need opaque names and an opaque content type.

`decryptConfidentialAttachment({ context, ciphertext, secretDescriptor })` bounds and strictly decodes the canonical descriptor, compares the expected room, epoch and attachment UUID, copies ciphertext, verifies its byte count and SHA-256 before decryption, and verifies AES-GCM authentication with the expected context. It returns plaintext only after authentication. Rewriting the descriptor context or digest cannot bypass the authentication tag. Unknown fields, duplicate keys, alternate JSON encodings, malformed Base64, unsafe epochs, resizable/shared buffers, accessors and oversized inputs refuse with one closed error. Caller buffers are never erased or retained as aliases. Owned key, IV, plaintext encryption copy and ciphertext temporary buffers are wiped on success or refusal where applicable. JavaScript strings and WebCrypto internal key allocations cannot be explicitly zeroized; no claim of complete memory erasure follows.

## Acceptance

The colocated Vitest suite uses actual WebCrypto to verify round-trip encryption, independent keys and IVs, copied caller inputs, public descriptor exclusion of secrets, wrong-context refusal including rewritten descriptors, digest-before-decrypt ordering, ciphertext authentication after digest rewriting, malformed descriptor refusal, input bounds and refusal when imported in a document context. Node WebCrypto unit evidence does not qualify browser worker execution, actual object storage or cross-client room delivery. No dependency, workflow or transport exception is introduced.

## Remaining room integration

The shipped native browser ABI and device worker currently support device creation, restore, registration and key-package publication. They do not expose room creation, Welcome join, durable room adoption/restore, ordered application receive, commit reconciliation or room application encryption. Rust already provides `OpenMlsDevice::create_room_and_persist`, `join_and_persist` and `DurableMlsRoom` operations. Connecting them requires a worker-private browser binding and a genuine trusted host for atomic device-plus-initial-room persistence, room checkpoint/pending-request CAS, accepted authority, read order and commit outcomes. A structural response object cannot replace those capabilities.

The Core relay has create/claim/commit/read/send operations but no channel-to-room discovery or eligible-device directory. Its currently active room roster can support ordinary send and removal checks, including the durable controller's rekey-required subset case, but does not discover eligible devices to add. Read responses omit historical sender keys after a sender leaves; the host needs an authenticated historical source or a resolver from pinned protocol state instead of assuming the current roster covers every envelope. The room host must resolve authoritative historical read and commit evidence, bind bootstrap Welcome to its actual recipient-specific envelope and pending MLS package, and reconcile uncertain sends using the same retained operation ID/body. New room provisioning and trusted membership discovery need explicit contracts before default room creation can work across clients.

This primitive is deliberately unconnected until that room pipeline can seal its secret descriptor. Existing ordinary attachment upload sends original bytes and metadata and must never be selected as a confidential fallback. Threads and reactions need authenticated encrypted application event schemas within the same room pipeline. Enabling a badge, changing an encryption flag or accepting opaque bytes does not establish those integrations. No claim of enabled end-to-end encrypted rooms, verified human identities, encrypted media or interoperability is made here.
