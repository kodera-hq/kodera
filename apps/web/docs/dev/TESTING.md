# Testing

Seven gates. Each one exists because of a specific failure that produces **no error message** — a green build and a wrong screen, or a green `main` and a published vulnerability nobody looked for. A gate that cannot fail is worse than no gate, so every one of them is written to be provably breakable.

## 1. Unit tests — Vitest + Testing Library

`npm run test`. Files at `src/**/*.test.{ts,tsx}` and `tests/unit/**/*.test.{ts,tsx}`, jsdom, setup in `tests/setup.ts`.

- Query the way a user finds things: `getByRole`, `getByLabelText`, accessible name. `getByTestId` is a last resort — a test id passes whether or not the element is reachable by a screen reader or a keyboard.
- The `.tsx` in the include glob is deliberate. The hub shipped `include: ['src/**/*.test.ts']` and every component test it later added was silently never run.
- No `passWithNoTests`. An empty suite must fail.
- `cleanup()` runs after each test: jsdom is shared inside a worker, and a component left mounted makes the next test's "should not be there" query find the leftover and pass wrongly.

## 2. End-to-end — Playwright against MSW

`tests/e2e/strict-csp.spec.ts` additionally builds the real OIDC application with MSW disabled and serves it through `server/static.mjs` on an ephemeral loopback port. It visits public login only, aborts nonlocal requests, forces every bundled font face to load and records CSP events before application startup. Both external font loading and absence of evaluation probes must pass under the unchanged strict policy. Each worker owns and closes its build directory, server and browser. `tests/unit/entry/csp-assets.test.ts` also builds a small real font using the production asset policy and verifies the emitted bytes and same-origin URL. These checks require neither staging access nor an identity transaction.

`npm run test:e2e`. Specs at `tests/e2e/*.spec.ts`, Chromium, `fr-FR` and `Europe/Paris`. Support code — fixtures and helpers, no assertions — sits beside them in `tests/e2e/support/`.

**Against a production build, never the dev server.** `webServer` runs `npm run build && npm run preview`: the dev server transforms sources on the fly and hides the failures that only appear bundled and minified.

**Against mocks, never a live Core API.** `VITE_ENABLE_MSW=1` starts the worker. A suite pointed at staging passes on staging's data, fails on a Tuesday, and tests nothing that a spec describes.

**The mock identity provider must never reach a real build.** `/__mock-idp/authorize` (`src/auth/mock-idp.tsx`) hands back a fixed authorization code to anyone who asks — fine for a suite that runs against mocks, a real vulnerability in a build a customer could load. `src/app/routeTree.ts` only adds the route when `VITE_ENABLE_MSW === '1' && VITE_AUTH_MODE === 'mock'`, and `src/main.tsx` only starts the MSW worker when `VITE_ENABLE_MSW === '1'` — both written as a literal comparison against `import.meta.env` at the exact point they guard a dynamic `import()`, not as a call into `src/config.ts`, so Vite's build-time replacement and the minifier's dead-code elimination can prove the branch false and drop the `import()` with it. `msw`'s service worker script (`msw/mockServiceWorker.js`) is gated the same way, one level down: it lives outside `public/` — which Vite copies to every dist root unconditionally — and a small plugin in `vite.config.ts` copies it in only for a mock build.

`npm run build:check` (`scripts/check-production-bundle.sh`) is what proves this stays true rather than a comment: it builds with `VITE_AUTH_MODE=oidc VITE_ENABLE_MSW=0` into a scratch directory and fails if the emitted JS contains `__mock-idp`, `mock-authorization-code`, `mock-idp` or `mockServiceWorker` — the mock IdP's own literals and the file name msw's worker requests — or if `mockServiceWorker.js` exists at the dist root at all. Its own self-test (`scripts/check-production-bundle.selftest.sh`) builds a mock configuration, which legitimately ships all four literals and the worker file, and asserts the check rejects the literals while confirming the worker file is still there — the control that proves the check is not vacuously green. Both run in the `bundle` job in CI (`.github/workflows/ci.yml`), not inside `npm run test`: they spend their budget on real `vite build` runs, which is a cost worth keeping out of the jsdom suite's loop. `tests/unit/production-bundle.test.ts` only asserts the check script and its self-test exist, are executable, and that `build:check` actually invokes the script — a cheap guard against the CI wiring silently pointing at nothing. `build:check` then runs the same script with `--profile staging`: the build the release playbook makes for staging (`VITE_FIRST_OWNER_JOURNEY=1`, deployment profiles `core_release_console_build_env`), which must carry the first-owner claim route `/claim/$organisationId` and `auth/claim-callback` and still none of the forbidden literals. Only the route proves the journey is built in: `auth/claim-callback` is in the production build too (`src/auth/oidc.ts`), and is required only so the scan matches the needles deployment profiles reads back. The same flag also opens order placement (`SUBMISSION_HELD` in `src/features/order/submission.ts`), so a staging build is the one where an order can be placed; the self-test proves a staging scan of a build without the route fails, and one with the mock IdP's literal fails. `src/app/routeTree.test.ts` carries the matching router-level tests: four for the runtime route table, one asserting `routeTree.ts` never contains a static `import … from './mock-idp-route'`.

Handlers come in two layers:

| Layer | Lives in | Hand-written? |
|---|---|---|
| Base handlers | `src/mocks/generated/`, generated from `kodera-server/contracts/core-api.openapi.yaml`, from the schema examples | No, and never hand-edited. Regenerated with the client — see [API_CLIENT.md](API_CLIENT.md). |
| Scenario overlays | `src/mocks/overlays/<area>.<condition>.ts` | Yes, and only these. Provisioning in progress, domain verification failing, invoice overdue, capacity at 92 %, permission denied, token expired mid-flow. |

Both layers live under `src/` because Vite has to bundle them for the preview build the suite drives and for Storybook (ADR-0005). Overlays are discovered with `import.meta.glob`, so adding one is a new file and nothing else: there is no registry to edit, and therefore no file every builder conflicts on. A spec activates an overlay by name through `tests/e2e/support/useScenario.ts`, which writes `sessionStorage['msw:scenarios']` before the application boots.

Hand-writing a base response is how a mock drifts from the contract: the console keeps passing against a shape the Core API stopped returning. If an overlay needs a field the spec does not have, the fix is a spec change in `kodera-core`, not a richer mock.

Every spec asserts on a message-catalogue key's rendered French, not on an English string that no customer sees.

## 3. Accessibility — axe, in two places

WCAG AA is a gate, not polish (AGENTS.md).

- **Storybook**, `@storybook/addon-a11y`: every primitive in `src/ui/`, in each of its states — default, hover, active, focus-visible, disabled, loading, error, empty, skeleton. `a11y: { test: 'error' }` in `.storybook/preview.ts` means a violation fails the story rather than colouring a panel nobody opens.
- **`npm test`**, `src/ui/stories-a11y.test.tsx`: the same stories, headlessly, in the `checks` job. It globs `src/ui/**/*.stories.tsx`, renders each story through Storybook's portable-stories API with the real preview annotations applied, runs the story's `play` function, and only then runs axe over it. A new primitive is covered as soon as its stories exist, not when somebody remembers to list it.

  Running `play` is what makes the state a story is *about* the state that gets judged: a focus ring, an opened menu, a field mid-error. Without it axe judges the first paint of a story whose point is what happens after an interaction. Note that portable stories render a story, they do not run the addons — `a11y: { test: 'error' }` in `.storybook/preview.ts` governs the Storybook UI, and the explicit `axe.run` in this file is the gate. `setProjectAnnotations` is called at module scope because `composeStories` runs while the file is being evaluated.
- **Playwright**, `@axe-core/playwright`: one scan per flow, on the states a story cannot reach — a form mid-error, a dialog open over a disabled background, a table after a filter empties it. A screen whose own spec carries no scan — a placeholder page, a page outside the shell, a step a flow only passes through — is scanned in `tests/e2e/axe-screens.spec.ts`, with no rule switched off and nothing excluded.

Two notes on how the headless run is wired, both of which are trade-offs rather than details:

- **Not `@storybook/addon-vitest`**, which is the documented route. It declares `@vitest/browser` and `@vitest/browser-playwright` as peers and runs every story in a real browser; the `checks` job installs no browser — only the end-to-end job does — so adopting it would mean a workflow change, and a gate that cannot run is not a gate. Portable stories cover the same story files with no browser.
- **`color-contrast` is disabled in that run.** jsdom performs no layout and applies no stylesheet, so axe cannot measure a ratio and would report the rule as *incomplete* — neither a pass nor a failure, and easy to mistake for a pass. Contrast is guarded where the values are, in the tokens repository's contrast table (ADR-0004), and by hand on the states axe cannot reach. **The console's own composition is therefore not contrast-checked anywhere yet**; the Playwright pass is where that lands, since it runs against a real browser with the real stylesheet.

The gate carries two mutations of its own, both permanent:

- a button with no name, handed straight to axe, which must be reported as `button-name`. An axe run pointed at the wrong element, or an assertion reading a field that has been renamed, passes every story silently.
- a fixture story whose `play` injects that same unlabelled button. Delete the `play` call from the runner and every real story still passes, because the violations it would then miss are exactly the ones that appear only after an interaction. This makes the deletion loud.

Two things axe cannot see, so they are checked by hand and asked about in the PR template:

- **Focus visibility.** axe checks that an element is focusable, not that you can *see* where the focus is. A focus ring that fails contrast against its surface, or a `focus-visible` style overridden by a later rule, is invisible to axe and to a mouse user, and makes the screen unusable by keyboard. Tab through the flow.
- **State carried by colour alone.** A red border with no text is a passing contrast check and an unreadable status.

## 4. Design tokens

The one guard that outranks the rest, because its failure is completely silent: a Tailwind class naming a token that does not exist emits **no CSS rule and no error**. The class stays in the markup, the element falls back to preflight, and `border-*` becomes `border: 0 solid #e5e7eb` — a light grey line on a dark page. The hub shipped that on two membership cards.

`tests/unit/ui/tokens.test.ts` runs the guard the tokens package publishes (`@kodera/design-tokens/token-test`), so the hub and the console judge their markup with the same scanner against the same preset.

The same file then closes the three ways of writing a colour that scanner cannot see, over the same walk plus `src/index.css`: an inline hex anywhere in a source file — the regex `tests/unit/toolchain.test.ts` applies to `tailwind.config.ts`, pointed at the source tree as well, and the only check that reaches a `style` prop; a class naming one of Tailwind's own colour families, which stay live beside ours because `theme.extend.colors` extends the palette rather than replacing it; and an arbitrary value on a colour utility (`bg-[…]`), whose opening bracket the scanner's character class stops at by construction. Each of the three emits a real CSS rule, so not one of them shows the silent-failure symptom above, and each ships a mutation fixture of its own. The set of Tailwind-stock families is derived, not listed — from the preset and the default palette in `tailwindcss/theme.css` (`tests/unit/ui/tailwind.ts`) — and is asserted to contain `blue` and to contain neither `cobalt` nor `transparent`, so a set that quietly emptied cannot let the check pass on anything.

The resolution check carries two self-checks the original taught us to keep:

- it asserts it scanned a non-trivial number of files, so a broken directory walker cannot make every assertion pass vacuously;
- it asserts it matched a non-trivial number of real token classes, so the matcher cannot be silently matching nothing.

This shape now guards three gates the same way — the token guard's file/match floors above, the spacing guard's own file/match floors (`tests/unit/ui/spacing-guard.test.ts`, §4 below), and the story gate's minimum story-file count (`src/ui/stories-a11y.test.tsx`, §3 above). Each floor is set to roughly 80% of what it measured the last time it was raised, so deleting the UI or breaking the scanner is loud while adding one more primitive is not. Raise a floor when a wave adds files; leaving it where it is is how a floor stops being one.

It also carries the mutation, permanently: a fixture naming `bg-cobalt-450` — a real family, a step that does not exist — which the guard must report rather than skip.

The token, spacing and theme-role guards walk `src/` with the tokens package's own `sourceFiles`, called with its default. Since v0.1.1 that default skips `node_modules`, `dist` and `.git` only as whole path segments below `src/`; before it, the pattern was tested against the whole absolute path, which skipped `src/features/distribution/` and every file of a checkout under a `dist` or `.github` directory. `tests/unit/ui/sourceFiles.test.ts` builds each of those trees, so a repin that brings the old walk back fails there.

`tests/unit/toolchain.test.ts` still fails if `tailwind.config.ts` declares any colour of its own. The two are complementary: the toolchain test forbids a second source of truth, the token test catches a class that names nothing in the first one.

**What the guard does not see.** It judges `bg-/text-/border-/ring-/fill-/stroke-` classes whose first segment names one of our colour families. A class naming no family at all (`text-inverse`, say, where the preset's key is `text-inverse` and the utility is therefore `text-text-inverse`) resolves to nothing and is skipped by construction, because the scanner cannot tell it apart from `text-center`. So is a side-specific border colour (`border-l-red-500`), whose first segment is the side. Use the themed roles — `text-c-ink`, `bg-c-action`, `bg-c-surface` — which are inside a family, are checked, and follow the theme.

**Only the `c-*` roles follow the theme.** The preset's other colour keys (`ink`, `surface`, `slate-*`, `cobalt-*`, …) are static values, painted light in every theme. `tests/unit/ui/theme-roles.test.ts` refuses, anywhere under `src/`, a static colour class on any Tailwind colour utility (side-specific borders, `divide-`, `outline-`, `ring-offset-` and Tailwind 4's `inset-shadow-`, `inset-ring-`, `text-shadow-` and `drop-shadow-` included), from the preset or from Tailwind's default palette it extends; an arbitrary value that carries a colour — a hex, a colour function, `theme(…)`, one of the 148 CSS named colours, or a variable that is not a `--c-*` role, as `var(--x)` or Tailwind's `[--x]` shorthand (`shadow-[…rgba(…)]`, `bg-[red]`, `text-[color:red]`, `bg-[--slate-900]`); and a literal colour written inside an inline `style={{ … }}`: a colour property that is not a `var(--c-*)` role or a keyword, or a shorthand (`background`, `border`, `outline`, `boxShadow`, `textShadow`) carrying one of the colours above. A style object built elsewhere, a value computed at run time, a colour property missing from that list, and an arbitrary value whose type hint is not `color:` are not judged. It also refuses an opacity modifier on a role (`bg-c-surface/40`), which the token guard cannot see, since its scanner stops at `/`. Under Tailwind 3 such a class compiled to no CSS rule at all, because a `var()` colour has no channels to scale — measured on the pinned preset. Tailwind 4 compiles it to a `color-mix()`, so one would start painting: allowing it is a design decision, not a cleanup. The few classes with no themed role yet sit in an allowlist bound to their file, which fails once an entry matches nothing. Its floors follow the same 80% rule.

**Tailwind 4 is held at Tailwind 3's rendering.** `src/index.css` carries a handful of lines that keep a Tailwind 4 behaviour at its Tailwind 3 value: the preset's font sizes without Tailwind 4's paired line heights, the default ring colour and transition duration the preset names, `hover:` on every device, the default border colour, the button pointer and the disabled cursor, and the tokens file below the utilities with the layer order declared first. Dropping any one repaints screens with no error, so `tests/unit/ui/tailwind-compat.test.ts` compiles each and fails on its own (the ring colour is `focus-ring.test.ts`'s), and refuses `outline-none` under `src/`, whose Tailwind 4 meaning drops the outline a forced-colours display shows on focus. [`docs/specs/tailwind-4-migration.md`](../specs/tailwind-4-migration.md) has the inventory.

Contrast pairs are guarded in the tokens repository, in the shape `kodera-visio/scripts/check-contrast.py` already consumes — an explicit table of (foreground, background, label, minimum), with missing tokens reported as SKIP and counted, so a rename cannot quietly empty the table.

`tests/unit/ui/spacing-guard.test.ts` runs the same self-checked pattern against spacing/size utilities (`h`, `w`, `p*`, `m*`, `gap*`, `inset`, …) and `font-*` weight utilities, reading the preset's `spacing` and `fontWeight` keys at test time. Unlike an unresolved colour these still emit a real rule — Tailwind's own scale is the silent fallback — so the failure is a size or weight off our grid, not a missing style.

## 5. Contract drift

Two checks, both in CI, described in [API_CLIENT.md](API_CLIENT.md):

- the committed generated client matches what the pinned spec generates today — a hand-edit to generated code fails here;
- the pinned spec version is not more than one minor behind what `kodera-core` publishes. Without this the console sits on an old contract indefinitely and nothing complains until a request 404s in production.

## 6. Dependency advisories

`node scripts/check-audit.mjs`, in the `advisories` job. Before it landed, `.github/workflows/ci.yml` carried no `npm audit`, no dependency-review and no advisory gate of any kind, so a high-severity advisory sat on a green `main` until Dependabot happened to open a pull request about it: nothing in the pipeline distinguished *no vulnerability* from *nobody looked*. Tracked as `B-no-audit-gate`.

**Any advisory at `moderate` or above fails the job, production dependency or development dependency alike.** One threshold, one mechanism, no tier that quietly does not block — a dev dependency runs in CI with repository credentials and on every engineer's machine, and a control that asserts less than a reader believes is the thing this file exists to prevent. Below the threshold an advisory is printed and blocks nothing; the printed row is how it stays visible rather than becoming a second, silent tier. The check passes `--include=dev` explicitly, because an `omit=dev` in an `.npmrc` would otherwise make the gate agree with a decision nobody took, and it refuses outright if the report it reads audited no development dependencies at all.

**An exception is never silent, and it is bound to the finding.** It is an entry in `npm-audit-allowlist.json` with a written `reason`. `advisory` is the identity — the GHSA identifier, or npm's numeric `source` when there is no GHSA — and `package`, `severity` and `range` must equal what `npm audit` reports today. Move any of them and the entry no longer describes the finding, so the gate fails rather than inheriting the old reason: an advisory re-pointed at another package, a severity that changed in either direction, a vulnerable range that widened or narrowed. An entry whose advisory has dropped below the threshold is deleted rather than re-bound, and fails until it is. An entry naming an advisory this audit does not report at all fails too, so a stale excuse cannot sit in the file waiting to cover a finding nobody decided. The rule splits at the threshold, and only one half ever fires on a row. That is the shape `contrast-known-failures.json` already has in `kodera-design-tokens` (`bindingProblem` in its `scripts/check-contrast.mjs`), deliberately: two repositories, one idea.

The allowlist ships empty. `npm audit` on this tree reports 0 vulnerable packages — 0 info, 0 low, 0 moderate, 0 high, 0 critical — across 753 packages.

Two numbers come out of `npm audit --json` and they are not the same one, so both are printed: `metadata.vulnerabilities` counts vulnerable **packages**, including every package that is vulnerable only because something it depends on is, while the advisories themselves are the `via` objects, and only those carry an identifier, a severity and a vulnerable range for an entry to be bound to.

`npm audit` exits non-zero whenever it finds *anything*, so the check parses the report first and decides afterwards. A check that branched on the exit code would read "there is an informational advisory", "there is a critical advisory" and "the registry was unreachable" as one event. `scripts/check-audit.selftest.sh` runs sixteen cases and each asserts the **message**, not the exit code — a blocking advisory with no entry, each bound field moved in turn, an entry with no reason, an entry whose advisory no longer blocks, an orphan entry, an unreadable report, a report with no counts, a non-zero exit over a report listing nothing, an advisory with no identifier, an unreadable allowlist, a dev-blind audit, and three that must be *accepted*: a below-threshold advisory, a correctly bound entry, and the real tree. CI runs it immediately before the check, the same way the bundle gate proves itself.

## 7. Visual acceptance — screenshots in one pinned renderer

`tests/visual/screens.spec.ts`, run by `playwright.visual.config.ts` and the `visual` job.

- One baseline per launch view, of its first screen at 1440 × 900, on the end-to-end suite's build, mock API and locale, with a fixed clock, reduced motion and bundled fonts. Not the full page: the shell is sticky and one viewport tall, so a full-page capture draws it once over a blank ground, a picture nobody sees. No masks: a masked region is a region not judged. Placeholder screens have no baseline; a screen gains one when it is built.
- One renderer writes baselines: the Playwright image pinned by digest, in CI and through `npm run test:visual`. A baseline from any other machine is a false difference. Screenshots compare at `threshold: 0`, and then through the decoded RGBA comparator (`tests/visual/support/exactBaseline.ts`): Playwright's comparator skips any differing pixel it takes for anti-aliasing and cannot be told not to, so a 1 px edge in the wrong colour (`#C9D3DE` instead of `#7C8894`) passed at threshold 0. `exactBaseline.ts` decodes both PNGs and enforces zero dimension mismatch and byte-identical pixels (`maxChannelDelta === 0`), with one bounded exception for Chromium's 1-in-16 outlined-button corner anti-aliasing flake (`order` 16 px, `invoices` 24 px, `invoice-detail-1024`): at most `MAX_CORNER_AA_PIXELS = 24` pixels across the screenshot may differ by at most `MAX_CORNER_AA_CHANNEL_DELTA = 2` (`Math.max(|dR|, |dG|, |dB|, |dA|) <= 2`). Any pixel with channel delta `> 2` (such as a token or border colour change, where `|dR| = 77` on `#C9D3DE` vs `#7C8894`) or more than 24 differing pixels fails the check and writes `<name>-exact-actual.png` to the `visual-diff` artifact. `--disable-skia-runtime-opts` was tested and removed after measurement in the pinned container showed the 1-in-16 corner variance persisted with the flag. One screen has a count of its own (`CORNER_AA_PIXELS_BY_BASELINE`): Chromium draws `order-dark` one of two ways, in about half of CI's runs and on every CPU model seen, the second differing at 41 corner pixels (38 at delta 1, 3 at delta 2) byte-identically from run to run, and never in the same image emulated on Apple silicon. A new baseline would only swap which drawing fails, so `order-dark.png` alone allows 48 pixels, still at delta 2 or less. Each worker prints `VISUAL_RENDERER_CPU`. Playwright's default of 0.2 counts a smaller per-pixel colour change as identical, and passed a shift of every ink role on every screen. Update with `npm run test:visual -- --update-snapshots`, read every changed image, and name each intentional difference in the pull request.
- A `@playwright/test` bump changes the browser, so it moves the image tag and digest (`scripts/visual.sh`, `ci.yml`) and regenerates the baselines in the same pull request.
- The `visual` job runs only when a change reaches its paths, and on every doubt: `ci-plan.py`'s `PATH_SCOPED` lists them (`src/`, `public/`, `index.html`, `msw/`, `server/`, `tests/visual/`, the Playwright, Tailwind, Vite and TypeScript configurations, the dependencies, `.nvmrc`, `scripts/visual.sh`, the workflows and the plan). A change elsewhere, such as docs or another suite, cannot move a baseline's pixel. A draft pull request skips it with every other job the plan may skip. It stays on the amd64 `ubuntu-latest` runner the pinned image is built for.
- The suite proves itself: the existing light/dark Home mutation controls pass their baseline, repaint one colour role by two levels per channel, and must then see a pixel difference. `visual/mutation-invoice-1024` does the same on the actual light invoice at 1024 × 800, with the same zero threshold as every other assertion, for both baseline and repaint. A setup or baseline failure cannot satisfy the refusal; the repaint must produce the actual pixel-difference message. Mutation controls skip when updating all/changed snapshots so a repaint is never written as a baseline. These finite repaint controls do not prove detection of every tiny colour or glyph change. The repaint is subtle on purpose — a loud one also passes a gate too lax to see a real role shift.

## Writing a test that can actually fail

Before a check is worth trusting, break the thing it guards on purpose and watch it go red. Where a check protects a gate rather than a feature, add the mutation as a test of its own: a suite that has quietly stopped detecting its bug is the failure mode every one of these gates exists to prevent.
