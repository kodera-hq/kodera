# Copy and internationalisation

**French is the product language. English is the second one. No string a customer can read is written inline in a component.**

The reader is the CEO of a 120-person construction company. Copy is judged by whether that person can act on it alone.

## Key convention

```
console.<area>.<screen>.<key>
```

`<area>` is one of the seven launch areas — `order`, `status`, `people`, `domain`, `invoices`, `support`, `federation` — plus `common` for what is genuinely shared (`common.action.cancel`, `common.error.network`).

```
console.domain.verify.title
console.domain.verify.cname.instructions
console.domain.verify.error.nxdomain
console.people.invite.csv.summary
console.invoices.list.empty
```

Keys are English, lowercase, dot-separated, verb-led where they name an action. `console.people.invite.button` says nothing; `console.people.invite.submit` says what happens.

Shared means *the same sentence in both places for the same reason*. Two screens that happen to both say "Continuer" today are not shared: promote a key to `common` only when changing it in one place must change it in the other.

## Rules

1. **Never inline.** A string in a component ships untranslated to every English user, and nothing fails. The PR template asks about it explicitly.
2. **Never build a sentence by concatenation.** `t('a') + name + t('b')` produces correct French and broken everything else. Use interpolation: `t('console.people.invite.sent', { email })`.
3. **Both catalogues in the same PR.** A key present in French and missing in English falls back to the key itself — `console.domain.verify.title` rendered on the page, in production, with no error.
4. **ICU plurals**, never a hand-rolled `n > 1`. French and English do not agree on zero and one:

   ```json
   "console.people.list.count_one": "{{count}} personne",
   "console.people.list.count_other": "{{count}} personnes"
   ```

   French uses the singular for 0 and 1 ("0 personne"); English uses the plural for 0 ("0 people"). A `count === 1` ternary is wrong in one of the two languages every time.
5. **Vouvoiement**, always. Verb-led buttons ("Inviter", "Vérifier le domaine", "Payer la facture"), never "OK" or "Soumettre".
6. **An error names the cause and the next action.** "Le domaine n'est pas encore vérifié. Ajoutez l'enregistrement TXT ci-dessous, puis relancez la vérification." — never "Erreur 409".
7. **No copy in a screenshot or an image.** It cannot be translated and it cannot be read aloud.

## French typography

These are not preferences; getting them wrong is what makes an interface look foreign to the reader it was written for.

- **Narrow no-break space (U+202F) before `?`, `!`, `;`, `:`** and inside `«  »`. A regular space lets the punctuation wrap to the next line alone.
- **Money: `5,99 €`** — comma as the decimal separator, a no-break space (U+00A0) before the euro sign, symbol after the amount. Never `€5.99`, never `5.99€`.
- **Thousands separated by a no-break space**: `12 500 €`.
- **Dates in full**: `2 septembre 2026`, not `02/09/2026`, which reads as February in English.
- **Percentages**: `92 %`, with a no-break space.

Format money and dates through `Intl.NumberFormat` / `Intl.DateTimeFormat` with the active locale rather than in a template string — those produce the right separators and spaces for both languages, and hand-written ones drift. Amounts arrive from the Core API as **minor units** (integer cents); divide once, at the formatting boundary, never in a component.

The Playwright suite runs under `fr-FR` and `Europe/Paris` so that assertions see exactly what a customer sees.

## The support address

A sentence that tells the customer to write gives the address: « écrivez-nous à {email} ». The
placeholder is filled by the runtime itself (`interpolation.defaultVariables` in
`src/i18n/index.ts`) with the console's one support address, `SUPPORT_EMAIL`
(`src/app/supportContact.ts`), so no call has to pass it and none can print the bare
placeholder. Never write the address in a catalogue: `src/app/supportContact.test.ts` fails on
one.

A sentence whose `{email}` means something else — the signatory's address on the order — passes
its own value, which wins over the default. Such a key is listed in
`src/app/supportSentences.test.ts`, which then checks that every call passes one: unlisted, a
forgotten value would be replaced by the support address without anything noticing.

## Adding a key

1. Add it to the French catalogue with the copy from the spec issue, which already carries the key and its text.
2. Add the English in the same PR.
3. Reference it by key in the component; the string appears nowhere else.
4. Assert on the rendered French in the test, not on an English fallback.

## Generated catalogues

`docs/specs/copy/fr.md` and `docs/specs/copy/en.md` are the source of truth. `src/i18n/fr.json`
and `src/i18n/en.json` are generated from them by `scripts/i18n/generate.ts` and are **never
hand-edited** — a hand-edit survives exactly until the next regeneration.

```
npm run i18n:generate
```

parses both markdown tables, converts `{name}` placeholders to i18next's `{{name}}`, expands an
inline ICU plural cell (`{count, plural, one {…} other {…}}`) into the i18next JSON v4 keys
`<key>_one` / `<key>_other`. An optional `many {…}` before `other` generates `<key>_many`: French
selects this category for whole multiples of a million. Keep the category in both catalogues
for JSON key parity, using each language's plural sentence. The generator fails loudly on a
key missing from one catalogue, a duplicate
key, a malformed table row, or a key that does not match the grammar above. Run it after any
change to either markdown file and commit the regenerated JSON in the same PR.

`npm run i18n:check` scans `src/**/*.{ts,tsx}` for `t('console….')` literals and fails on any key
absent from the generated catalogues — the product-code counterpart to
`scripts/check-copy-keys.py`, which checks the markdown against `docs/specs/`.
