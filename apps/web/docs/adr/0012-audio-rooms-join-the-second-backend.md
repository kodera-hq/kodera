# ADR-0012: Audio rooms join the second backend, and every organisation's homeserver is found under one matrix domain

**Status:** Accepted (owner decision in chat, 2026-10-28); supersedes ADR-0011 in part (the form of `connect-src`, and its consequence of one homeserver per deployment)
**Deciders:** zôÖma (messaging-pilot design §2.7, which approves LiveKit as the second exception); the lead (how the homeserver is found, and the form of the CSP)

## Context
ADR-0011 gives the Console a second backend, the workspace's Synapse, and names it in the CSP as `{homeserver}/_matrix/` "and nothing else". It leaves LiveKit's signalling to its own change.

Espace's audio rooms run on LiveKit. Joining one needs a LiveKit token for that room. The room-access service on the tenant's VM (kodera-core `room_access/`) issues it in exchange for the member's own Matrix access token, after checking that the member is a joined member of the room. The tenant edge routes that service on the homeserver's own origin, at `POST /_kodera/rooms/token`. The Console then connects to the tenant's LiveKit server over `wss://`.

ADR-0011 also leaves the Console with no way to learn a homeserver: the static server is given one `--homeserver-origin`, and nothing in the Console knows which homeserver an organisation has. Every organisation has its own, on its own VM. Core's contract has no field for it, and none is added for the pilot.

## Decision
- **The homeserver is derived, by one function.** The Matrix server name is `{organisation slug}.{matrix domain}`. The matrix domain is a setting per environment: `kodera.io` in production, `staging.kodera.io` on staging; the Console reads it from `VITE_MATRIX_DOMAIN`, the static server from `--matrix-domain`. The homeserver is found by standard Matrix client discovery: `GET https://{server name}/.well-known/matrix/client`, without credentials, whose `m.homeserver.base_url` the tenant profile serves with CORS `*`. A 404 means `https://{server name}` (the spec's IGNORE); a document without a usable `m.homeserver` is the spec's FAIL_PROMPT and is refused. A base URL is accepted only on the organisation's server name or a host under it, and the room-access service's LiveKit URL only on the session's server name or under it: a tenant cannot point the Console at another tenant under the same matrix domain. A Matrix session is shown only in the workspace of the organisation whose server name its user ID carries: the Console keeps one session, from the last organisation opened. `src/features/espace/homeserver.ts` is the only code that derives it: a later per-organisation homeserver from Core (a customer's own domain) replaces that function and leaves its callers alone.
- **A discovered base URL is accepted only where the CSP lets the page go:** an `https` origin, on the default port, with no path, whose host is under the matrix domain. Anything else is refused, and the member is told Espace cannot open.
- **`connect-src` names every host under the matrix domain, on the paths the Console calls and no others.** `server/static.mjs` takes a required `--matrix-domain` (a lowercase DNS name of two labels at least, with no scheme, port, wildcard or trailing dot) and emits:
  - `https://*.{matrix domain}/.well-known/matrix/client`, discovery;
  - `https://*.{matrix domain}/_matrix/`, the client-server API, as ADR-0011 says;
  - `https://*.{matrix domain}/_kodera/rooms/token`, the room-access call, a path source with no trailing slash, so it matches that path and no other. It is called with the member's own Matrix token, as the client-server API is, by `src/features/espace/audio/roomAccess.ts` and by nothing else. ESLint names that file, and the resolver, next to ADR-0011's two;
  - `wss://*.{matrix domain}/rtc`, `/rtc/v1`, `/rtc/validate` and `/rtc/v1/validate`: LiveKit's signalling and, after a failed connection, its validation request. These are exactly the URLs the installed livekit-client builds under its server's URL; `tests/unit/serving/livekit-paths.test.ts` runs the SDK's own URL builders and holds the list to them.
- **No source under the wildcard is a bare host, `wss` included.** Under CSP Level 3 scheme matching, a `wss:` source also matches `https:` (and `ws:` matches `http:` and `https:`). A bare `wss://*.{matrix domain}` would therefore admit `https` to every path of every host under the domain, Core's and the identity provider's included, and undo every path rule above. A header test refuses any `connect-src` source other than `'self'` that names no path.
- **The LiveKit server is checked twice.** The room-access call refuses a grant whose LiveKit URL is not `wss:`, on the default port, with no path, on a host under the matrix domain, before anything connects; the CSP refuses it again in the browser.
- **The local stack is named only on request.** `--homeserver-origin` (an `http` or `https` origin on this machine) and `--livekit-origin` (a `ws` origin on this machine) remain for the test stack, emitting the same paths on those origins, and the server refuses either unless it is also given `--allow-loopback`, which no deployment passes, and refuses `--allow-loopback` given without either. `--livekit-origin` is no longer a deployment setting: LiveKit is covered by the matrix domain. The Console's development override, `VITE_ESPACE_DEV_HOMESERVER`, replaces discovery with a loopback origin in a development build only; a production build neither reads it nor accepts one. With it, every organisation's server name is the local stack's own, `VITE_ESPACE_DEV_SERVER_NAME` (`kodera.test` by default).
- **livekit-client stays behind Espace's call** (`src/features/espace/audio/`), as matrix-js-sdk stays behind its store. An ESLint rule refuses the import anywhere else.
- **No LiveKit token is kept or logged.** The Console asks for a new one at each join and hands it to the SDK only.

What ADR-0011 says about the Synapse client-server API is unchanged. Its "nothing else" for the homeserver's origin, and its one named homeserver, are replaced by the list above.

## Options considered
- **A homeserver URL per organisation in Core's contract.** Not now: no contract change for the pilot. The single resolver is where it lands when a customer brings its own domain.
- **The homeserver named exactly, per deployment (ADR-0011).** Rejected: one Console serves every organisation, each with its own homeserver, and the static server sends the CSP before anyone signs in.
- **A CSP per organisation, chosen per request** (ADR-0011's option, design §6). Rejected for the same reason: the page is served before any organisation is known.
- **A bare wildcard, `https://*.{matrix domain}` or `wss://*.{matrix domain}`.** Rejected: it opens every path of every Kodera host to anything running in the page. ADR-0011 rejected the wildcard for this reason; the path-limited form answers it.
- **LiveKit's signalling under a prefix (`wss://*.{matrix domain}/rtc/`).** Rejected for exact paths: a prefix also admits every other path under `/rtc/`, over `https` too, and the SDK opens four known ones.
- **Proxy the room-access call through Core.** Rejected for the reason ADR-0011 rejects proxying Matrix: Core would sit on the path of every join, and would have to hold or forward the member's Matrix token.

## Consequences
- **The wildcard also matches Kodera's own hosts.** `*.{matrix domain}` covers `app.`, `auth.`, Core's host and every other host under the domain, not just tenants'. They are reachable from the page only on the paths above, which no platform host is meant to serve; one that serves `/_matrix/`, `/_kodera/rooms/token`, `/.well-known/matrix/client` or `/rtc…` becomes reachable from the Console. The wildcard does not match the bare matrix domain, nor any other port than 443.
- **Discovery is one more request** before Espace opens, to a file the tenant profile must serve with CORS. A base URL with a path, though legal in Matrix, is refused: the CSP's paths are at the root.
- **A livekit-client upgrade that moves a path** fails `livekit-paths.test.ts`, and the CSP's list is changed with it. The SDK's other requests to its server, a `HEAD` to the server's root when the browser comes back online, and region discovery on LiveKit Cloud only, are refused by the CSP: the first costs the immediate reconnect on that event, and the SDK's own reconnection still runs.
- **Whoever deploys the Console** passes the matrix domain twice, at build (`VITE_MATRIX_DOMAIN`) and at serving (`--matrix-domain`), and the two must agree. Unset at build, the Console offers no live Espace and shows the workspace's layout only.
- **Every tenant is under the matrix domain.** A customer's own domain needs the per-organisation homeserver from Core, and a CSP that names it: that is the trigger to revisit this ADR.
