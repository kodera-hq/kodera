# Invitation entry bootstrap

Status: Draft source proposal; not implemented or qualified by this document.

Before verified URL cleanup, only navigation HTML and one same-origin self-contained external bootstrap response may load. No inline/eval script, theme, icon, manifest, CSS, preload dependency, app/auth SDK, worker, telemetry or provider/API request is permitted. This refines the selected policy in09-owner-claim.md without changing its eventual envelope/attempt or unresolved-recovery rules.

index.html names src/entry-bootstrap.ts as its only module entry. The existing theme script is dynamically loaded only after ordinary-page cleanup; the original icon/manifest/theme-color metadata is inert template content until then. Main exports the same boot body with its original i18n/MSW/router order and literal mock guards. The bootstrap's sole dynamic main import and call occur after cleanup and theme application. There is no second document/bootstrap redirect or new route.

The gate captures the opaque fragment once without decoding, uses replaceState with existing nonsecret history state, preserves query/path, and verifies the resulting URL. Failure, throw or no-op is unresolved; lexical fragment references are dropped before ordinary release or terminal recovery. This is bounded reference handling, not a heap-erasure claim. No fragment, URL or SDK transaction is written to storage, router, history data, globals or logs.

The root-path claim entry stops even after successful cleanup unless the first-owner journey is built in. /auth/claim-callback serves in every build, because an invitation's protected sign-in returns there too, and /invitations/accept/<UUID>/<slug> keeps its fragment, bounded to 32–256 printable characters, and hands it to the page in memory (12-invitation-accept.md §3). Descendant/encoded protected paths also fail closed; they grant no authority. The callback reads only kodera.owner-claim.entry.v1, removes an existing value without parsing it and verifies absence. Read/remove/readback failure leaves the gate unresolved. Ordinary/silent /auth/callback does not touch that key and retains its existing SDK-owned query handling only after independent cleanup. This root fixture does not qualify arbitrary deployment prefixes or provider registration.

There is no envelope producer, parsed schema, retry, consume POST, sign-in redirect, auth/claim handoff, registered-factor signal or Order grant here. The selected eventual one-envelope original ten-minute nonsliding lifetime, one redirect and one in-memory explicit attempt remain required for a separate connected slice. SUBMISSION_HELD remains true. Recovery asks the person to reopen the original invitation or contact the canonical support address; it never reconstructs an invitation URL or promises that reconnecting restores intent.

Four French source-catalogue keys and English translations provide plain unresolved-recovery text. The existing generator remains the only writer of runtime catalogues. At build time, Vite projects exactly those generated French strings plus canonical SUPPORT_EMAIL into inert HTML. It substitutes generated {{email}} and rejects unresolved placeholders, empty/invalid fields, missing marker and invalid data; escape every text field. No runtime i18n/React/full catalogue chunk or network lookup precedes cleanup. The fallback has semantic heading/paragraph/alert markup and no style/resource/action URL, button or handler.

The real Vite transformIndexHtml and generateBundle hooks use the exported renderer/guard. The bundle adapter passes actual modules/rendered lengths, imports, extracted CSS, code and dynamic main mapping. Executing bootstrap modules are only the exact entry ID and optional locked Vite preload-helper/modulepreload-polyfill IDs. Only the exact HTML entry facade may be zero-rendered additionally; no wildcard/query ID, unknown zero-length module, static chunk import, CSS or oversized entry is accepted. Preserve the global default modulepreload polyfill. Helpers must actually inline into the same response. The one dynamic target must contain real main.tsx; a synthetic metadata fixture or16KiB bound cannot prove runtime ordering.

Acceptance before connection requires ordinary existing CI with the real build, actual CLI and both Chromium projects: the existing ordering red must first reach EARLY_NON_BOOTSTRAP_FETCH on an actual current resource. Setup/lint/type/build errors are diagnostics. Then full browser checks verify protected/failure stops, exact requests, native timing, normal main request/execution, no-op/throw nonrelease, callback deletion, ordinary-callback isolation, foreign-storage/history-state controls, catalogue fallback and actual polyfill fallback. The build guard's finite negative controls/pristine checks accompany real build-hook execution and emitted-code review. Actual-source mutation probes require separate admission after pristine baseline; import/setup failures do not count as behavior kills.

Source HTTP headers, emitted graph, browser behavior, SDK/provider transaction and deployed operator evidence are separate qualifications. This proposal establishes none by itself. No host, deployment, workflow/dependency/configuration origin, provider URI registration or commercial backend is authorized here.
