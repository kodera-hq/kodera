# Tailwind 4 migration

Status: Accepted. The product owner accepted the supported-browser floor, ADR-0008, and regenerating the two login baselines whose corner anti-aliasing moved (Proof).

## Scope

Move the console from Tailwind CSS 3.4 to Tailwind 4 with **no change in layout, colour or style**: every element keeps its geometry and every computed style that paints. One difference remains in the pinned renderer, below the level of styles: on the login screen in the dark and black themes, seven or eight anti-aliasing pixels at the corners of the submit button differ by one level in one channel, and those two baselines were regenerated on the owner's ruling (Proof). It prepares the later UI and UX rework and is not part of it: no class is restyled, no token moves, and no other baseline is regenerated. The tokens package stays the single source of truth (ADR-0004): its Tailwind preset is loaded unchanged through `tailwind.config.ts`, which `src/index.css` names with `@config`, Tailwind 4's compatibility path. A CSS-first `@theme` built from the tokens belongs to the rework.

Tailwind 4 runs through `@tailwindcss/vite`. `@tailwindcss/postcss` was tried first and measured broken here: Tailwind rebuilds the rules Vite's own `@import` inlining hands it without their source file, so every relative `url()` of the self-hosted fonts fails to resolve at build time. The Vite plugin resolves `src/index.css`'s imports itself and rebases those URLs. `postcss.config.js` and `autoprefixer` go: Tailwind 4 prefixes through Lightning CSS for its own browser floor. The tests that read compiled CSS use `@tailwindcss/node`, the compiler the Vite plugin runs, through `tests/unit/ui/tailwind.ts`.

## Supported browsers

Tailwind 4 needs Safari 16.4+, Chrome and Edge 111+ and Firefox 128+ (`@property`, `color-mix()`, cascade layers). Below that floor the console's styles do not apply correctly. The product owner accepted this floor; nothing else is narrowed here.

Every row was checked against this codebase, not from the upgrade guide alone. "Held by" names the test that fails if the neutralisation is removed.

Classes whose declarations differ but render the same: logical properties (`padding-inline` for `px-*`, the console is left to right), individual `translate`/`rotate` for `transform` (same order), `flex: 1` for `1 1 0%`, `clip-path: inset(50%)` for `clip` in `sr-only`, an explicit `border-style: solid` beside the width, extra transparent zero-size shadows in `box-shadow`, `[hidden]` gaining `!important` (no element combines `hidden` with a display class), wider `transition-property` lists (no transitioned property changes), fractions to four decimals instead of six (`w-1/3`: under a thousandth of a pixel at any width), and the three static-colour opacity classes now precomputed as `oklab()`, which converts back to the same sRGB value and alpha.

## Opacity modifiers on token colours

Under Tailwind 3 an opacity modifier on a `var()`-backed colour (`bg-c-surface/40`) emitted no rule; Tailwind 4 emits a `color-mix()`, so such a class would start painting. There is none under `src/`, and `theme-roles.test.ts` already refuses every one. The three opacity classes that exist are on static hex colours (`border-red-500/40`, `border-amber-500/40`, `bg-red-100/60`, in `Banner`, `Button`, `LinkButton` and `Table`), and paint the same colour before and after.

## Proof

- The CSS a production build ships was compiled from the same sources under Tailwind 3 (main) and Tailwind 4 (this branch), parsed rule by rule, each rule's own Tailwind variables substituted, theme variables inlined and lengths and colours normalised, then compared for every selector. Every difference is in the table above.
- Every class combination an element can carry (the class-conflict guard's resolver, widened to all classes) was checked for two classes setting one property whose stylesheet order differs between the two builds: none. The check compares order only, not specificity. One selector's specificity did change: Tailwind 4 writes `group-data-[state=indeterminate]:*` as `:is(:where(.group)[data-state="indeterminate"] *)`, (0,2,0) where Tailwind 3's `.group[data-state="indeterminate"] .x` was (0,3,0). It is used only in `src/ui/Checkbox/Checkbox.tsx` (the two indicator spans), beside `hidden` (0,1,0), which it still beats.
- Each neutralisation in `src/index.css` that a test holds, removed alone, fails the tests named for it above and no other.
- The visual suite, in its pinned renderer on the Tailwind 3 baselines, passed every screen but two: `login-dark` and `login-black`, 7 and 8 pixels at the four corners of the full-width « Continuer » button, each one level in one channel. Measured in that renderer on both builds: the field and the button have the same geometry to the 1/64 px (`531, 487.3125, 378 × 40` for the button) and the same painting styles; swapping in Tailwind 3's stylesheet on the same DOM gives zero difference. What differs is transparent paint elsewhere on the page — the focused input's transparent 2 px outline (Tailwind 3's `outline-none`), and the extra transparent layers Tailwind 4's ring and shadow utilities put in `box-shadow`. Restoring the outline alone moves the ±1 pixels to the field's corners; only the outline together with Tailwind 3's three-layer ring or card shadow brings the difference to zero; Tailwind 3's page does not move under the same injections. The button's corner anti-aliasing thus depends on transparent paint around it, not on its own box or colour: a rasterisation difference that no compatibility line can remove short of overriding Tailwind 4's core ring and shadow utilities. The product owner ruled to regenerate those two baselines, and only those: regenerated in the pinned image, each new file differs from the old one in exactly the measured corner pixels (7 in dark, 8 in black, one level in one channel) and is identical to CI's own render of this branch; every other baseline is unchanged.
